# scrape-music-events

Daily scraper that pulls the weekly live-music and events schedule from
[Blue Wave Radio's Roatán Music Scene](https://www.bluewaveradio.live/roatanmusicscene)
(Keith's data, used with his permission), normalizes it into the iOS app's
`Event` schema, and uploads the JSON to Supabase Storage at
`app-data/events.json`.

The iOS app (`EventsService`) fetches this file on launch, refreshing at most
every 6 hours. The bundled `events.json` is the offline / first-launch fallback.

## How it works

The Blue Wave page is a Squarespace shell — the schedule itself is served by
Keith's Google Apps Script as a JSONP payload:

```
GET <BWR_EXEC>?fn=embed_js&cb=renderSchedule&v=BWR-JSONP-v9
→ renderSchedule("<style>...</style><div class=\"rms-wrap\">...")
```

We call that endpoint directly — the same data the website renders, with no
HTML-page scraping and no ScrapingBee. The payload markup is generated by the
Apps Script from Keith's spreadsheet, so its structure is stable:

```html
<div data-frag="week">                     <!-- also weekend + today frags; we parse ONLY week -->
  <section class="day" data-day="Monday">
    <li class="item" data-area="West Bay">
      <span class="venue">Beachers, West Bay | +504 8791-0058</span>
      <span class="tail">LIVE MUSIC · TOMMY MORRIS - Classics · <span class="time">@ 5:30 PM</span></span>
      <span class="addl">{ Every Monday }</span>   <!-- or instrumentation like "Guitar & Vocals" -->
```

Parsing details worth knowing:

- **Area** comes from the venue line ("…, Sandy Bay | …"), not `data-area` —
  Blue Wave groups everything east of West End into one "Sandy Bay & Beyond"
  bucket, while the venue text has the real area.
- **Dated one-offs** appear either as `<span class="date">[8/10/2026]</span>`
  or as a bracketed `[5-Aug]` text segment; both become `date: "yyyy-MM-dd"`
  and `recurring: false`.
- **Category labels** (LIVE MUSIC, BINGO NIGHT, GARIFUNA SHOW, …) map to the
  app's `EventCategory` raw values via `CATEGORY_MAP`; unknown labels fall
  back to "Special Event".
- **Featured ("Don't Miss") picks** are Josh's curation, re-applied by
  (day, venue, startTime) via the `FEATURED` table in `index.ts`. Update that
  table to change the featured set.

## Safety rails

- If fewer than `MIN_EVENTS` (15) rows parse, the run ABORTS without
  overwriting the existing `events.json`, and uploads the raw payload to
  `app-data/music_debug.txt` for inspection.
- Every run (success or failure) writes `app-data/music_status.json`:
  `{ ok, lastRun, source, count, ... }` — check this file first when
  debugging. It's public:
  `https://<project-ref>.supabase.co/storage/v1/object/public/app-data/music_status.json`

## Schedule

pg_cron job `music-events-daily`, `10 */2 * * *` — every two hours, UTC —
calling the function via `net.http_post`.

It used to run twice a day on `10 9,15 * * *`, which is island 03:10 and
09:10. The last read of the island day was therefore mid-morning, so
anything Keith changed after breakfast — which is most of what changes,
including that evening's lineup — did not reach a phone until 3am the next
morning. Live music is an evening product. Two-hourly caps the worst case at
about two hours behind the source, and the app's own hourly refresh puts the
end-to-end worst case around three.

## When it breaks

- **Apps Script endpoint changed:** Keith redeployed his script. Fetch the
  Blue Wave page and look for `var EXEC = "https://script.google.com/macros/s/..."`,
  update `BWR_EXEC`, redeploy.
- **Zero/low parse count:** the generated markup changed. Read
  `music_debug.txt`, adjust `parseEvents`/`parseItem`, redeploy.
- The failure mode is graceful either way: the app keeps serving the last
  good schedule (cached, then bundled) until the scrape recovers.
